# Архитектура отладки через эмулятор в проекте Slayers Royal (PS1)

> **Назначение документа:** подробное руководство для разработчиков и реверс-инженеров по методологии, скриптам и инструментам отладки модификаций PlayStation 1 в эмуляторе (на примере эмулятора **DuckStation**).

---

## 1. Концепция: Evidence-Grounded Debugging

В отличие от любительского ромхакинга методом «научного тыка», данный проект построен на доказательной отладке (Evidence-Grounded Debugging):
1. **Любое изменение диска верифицируется аппаратно до запуска эмулятора** (проверка контрольных сумм EDC/ECC, бюджетов секторов и указателей).
2. **Состояние оперативной памяти (RAM) и видеопамяти (VRAM) извлекается напрямую из эмулятора** через дампы сохранений (Save States) и фреймбуфера.
3. **Обновление текстов в памяти эмулятора происходит на лету** без необходимости перезапуска игры и выхода на карту мира (`tools/sync_savestates.py`).

---

## 2. DuckStation как главная отладочная станция

Для отладки PS1 в проекте выбран эмулятор **DuckStation** (доступен под Linux и Windows) по следующим причинам:
* Высокая точность эмуляции аппаратных таймингов процессора MIPS R3000A, геометрии GTE и чипа SPU.
* Встроенный **VRAM Viewer** с показом палитр CLUT и координат видеопамяти.
* Продвинутый дизассемблер и отладчик с поддержкой аппаратных точек останова (Hardware Memory Breakpoints на чтение и запись).
* Поддержка запуска из командной строки в пакетном режиме (Batch/CLI).

### 2.1. Запуск из скрипта с привязкой параметров
Скрипты `run_game.sh` (Linux) и `run_game.bat` (Windows) запускают эмулятор с автоматической передачей параметров:

```bash
# Запуск русского образа диска
./run_game.sh

# Запуск оригинального японского диска для сличения поведения
./run_game.sh --orig

# Автоматическая сборка перед запуском
./run_game.sh --build
```

Внутри Windows-лаунчера (`run_game.bat`) выполняется автопоиск установленного DuckStation:
```bat
if exist "%LOCALAPPDATA%\DuckStation\duckstation-qt-x64-ReleaseLTCG.exe" (
    set "EMU="%LOCALAPPDATA%\DuckStation\duckstation-qt-x64-ReleaseLTCG.exe""
)
...
start "" !EMU! "%TARGET_CUE%"
```

## 3. Живая синхронизация сейвстейтов RAM (`tools/sync_savestates.py`)

### 3.1. Проблема классического тестирования на эмуляторе
В архитектуре *Slayers Royal* при входе в город или локацию игровой движок считывает оверлей городских служб и диалогов (**`PROG.UNT Entry 3`**) в оперативную память по базовому адресу **`0x8004E5B0`**.
* Если вы тестируете диалог в таверне, делаете быстрое сохранение (Save State, `F2`) и затем находите опечатку — простое пересобирание диска `slayers_royal_ru.bin` **не изменит текст в игре при загрузке сейвстейта**!
* При нажатии `F3` (Load State) эмулятор восстановит старый снимок RAM `0x8004E5B0` с диска на момент входа в город. Чтобы увидеть новый текст, ромхакеру приходилось каждый раз выходить из города на глобальную карту и заходить обратно.

### 3.2. Решение: Инжектор в память сейвстейта
Разработан скрипт `tools/sync_savestates.py`, который:
1. Находит файлы быстрых сохранений DuckStation:
   * Windows: `%USERPROFILE%\Documents\DuckStation\savestates\ss_SLPS-01363_*.sav`
   * Linux: `~/.local/share/duckstation/savestates/ss_SLPS-01363_*.sav`
2. Распаковывает сжатый zlib-контейнер сейвстейта.
3. Сканирует 2 МБ оперативной памяти PlayStation (RAM `0x80000000..0x80200000`).
4. Находит смещение `0x8004E5B0` и напрямую заменяет текстовые буферы и 32-битные указатели на свежие русские данные из `translations/`.
5. Перепаковывает `.sav`.

**Результат для разработчика:**
Вы правите текст в JSON $\to$ запускаете `python tools/sync_savestates.py` $\to$ нажимаете `F3` в эмуляторе $\to$ текст мгновенно обновляется прямо на экране диалога без перезагрузки игры.

## 4. Инспекция видеопамяти VRAM и реверс шрифтов

Видеоконтроллер PlayStation 1 (GPU) оперирует единым фреймбуфером размером **$1024 \times 512$ пикселей** с 16-битной глубиной цвета.

### 4.1. Использование VRAM Viewer в DuckStation
Нажатие клавиши `F10` (или меню `Tools -> VRAM Viewer`) открывает интерактивную карту видеочипа:
* При наведении курсора мыши на любой пиксель отображаются:
  * Координаты в VRAM: $(X, Y)$ в диапазоне $0..1023$ и $0..511$.
  * Глубина цвета текущей поверхности: 4bpp (16 цветов), 8bpp (256 цветов) или 16bpp Direct Color.
  * Координаты палитры (CLUT): $(X_{\text{clut}}, Y_{\text{clut}})$, например `(0, 480)`.

### 4.2. Диагностика шрифтовой подсистемы
В ходе проекта с помощью VRAM-дампов были выявлены и устранены фундаментальные ошибки:

1. **2BPP-формат боевого шрифта (`Entry 0x142`):**
   * Дамп VRAM `data/sav_spell_font_960_256.png` и сетка `data/combat_font_reference_grid.png` показали, что боевой движок распаковывает глифы на лету из 2-битного формата (2 бита на пиксель, 64 байта на тайл $16 \times 16$), а не 4bpp со страйдом 128.
   * Формула адресации тайла в памяти:
     $$\text{offset} = 544 + \text{bank} \times 16384 + (\text{row} \times 16 + y) \times 64 + \text{col} \times 4$$
   * Исправление формулы в `tools/patch_combat_font.py` полностью устранило появление японских кандзи в бою.

2. **Защита контроллерных глифов в `SMINI.UNT`:**
   * Просмотр VRAM показал, что в мини-игре Амелии (`SMINI.UNT Entry 1`) ячейки `0x006B` (кнопка `○`), `0x0074` (`↑`), `0x0075` (`↓`), `0x0076` (`→`), `0x0077` (`←`) содержат аппаратные иконки кнопок геймпада.
   * Старый патчер перезаписывал их кириллицей, вызывая «кракозябры» в окне комбинаций. Введение списка `SMINI_PROTECTED_GLYPHS` исключило порчу служебных глифов.

3. **Ликвидация сдвига шрифта +1 (Цезарь-баг «Пвже / Тыжцэ»):**
   * Сравнение VRAM-атласа с эталоном `translations/glyph_map_ru.json` выявило, что символы в мини-играх рендерились со сдвигом на +1 (`А` = 0x0008 вместо 0x0007). Синхронизация таблиц устранила баг во всех мини-играх.

## 5. Отладка коллизий памяти RAM (Кейс города Сония: 0x03E vs 0x058)

Один из сложнейших багов, решённый через эмулятор — зависание эмулятора с чёрным экраном при ночлеге в Отеле Сонии.

### 5.1. Трассировка адресов памяти MIPS
1. В эмуляторе была установлена точка останова на выполнение исключения `Address Error Exception (Load/Store)`.
2. Процессор MIPS выбросил исключение по адресу `0x8003XXXX` при попытке перехода по указателю `0x7FF04F6D`.
3. Анализ карты RAM показал:
   * Текущая сцена диалогов распаковывается по базовому адресу: **`0x80121000`**.
   * Следующий системный контейнер комнат **`PROG.UNT 0x058`** загружается по жёстко зашитому адресу: **`0x8012A800`**.
   * Допустимый физический объём буфера сцены:
     $$\Delta = \text{0x8012A800} - \text{0x80121000} = 38\,912 \text{ байт} = \mathbf{19 \text{ секторов}}$$
4. Старый патчер выделил сцене Сонии 32 сектора (65 КБ). Загрузившийся блок `0x058` физически перезаписал хвост сцены Сонии с таблицей указателей. При вызове события отеля `0x04A6` движок прочитал мусор вместо указателя.

### 5.2. Инженерное решение
* Сцена `0x03E` была жёстко зафиксирована в объёме строго **19 секторов (38 912 байт)**.
* Для сохранения полного литературного текста Ren'Py было внедрено изолированное сжатие **Scoped Compact Glyphs (DTE)** на 220 токенов во VRAM (`PROG.UNT 0x03A`).
* Это сэкономило 27,4 КБ и предотвратило перекрытие буферов (коллизия строго 0 байт).
* В сборочный конвейер `build.sh` добавлен автоматический страж:
  ```bash
  python3 tools/verify_scene_budget.py --bin "$RU_BIN"
  ```
  Он прерывает сборку, если хотя бы одна сцена превышает 19 секторов.

## 6. Аппаратные точки останова (Hardware Breakpoints) в DuckStation

Чтобы найти функцию движка, отвечающую за конкретное действие:
1. Откройте в DuckStation: `Debug -> Memory -> Go to Address`.
2. Введите известный адрес RAM (например, `0x8006D0BC` — счётчик съеденных тарелок Лины в мини-игре «Обед»).
3. Кликните правой кнопкой мыши по ячейке $\to$ `Add Breakpoint` $\to$ `Break on Write`.
4. Возобновите игру (`F5`).
5. Как только Лина съест блюдо, эмулятор мгновенно остановит выполнение на инструкции процессора:
   ```mips
   0x800507B4: sb $v0, -12100($at)  # запись +1 очка в RAM 0x8006D0BC
   ```
6. В окне регистров видны все аргументы: тип блюда в `$v1`, таймер в `$a0`, адрес возврата в `$ra`.

## 7. Контрольные суммы секторов (EDC/ECC Guard)

Перед запуском игры в эмуляторе всегда запускается валидатор:
```cmd
build.bat --validate
```
Он проверяет целостность Mode 2 Form 1 EDC/ECC для каждого модифицированного сектора диска. Если контрольная сумма не сходится, сборщик укажет конкретный номер LBA, предотвращая запуск повреждённого образа.
